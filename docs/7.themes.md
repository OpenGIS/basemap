# Theme System

> How the dark-first distribution derives two published styles from one upstream recompose, and where the map theme, icon palettes and site tokens fit together.

## Overview

Basemap publishes two styles from a single OpenMapTiles recompose:

| Output | Published file | Contract |
| --- | --- | --- |
| Basemap Dark (default) | `style.json` | The light clone with the strict ordered dark theme applied |
| Basemap Light | `style-light.json` | A cartographic no-op of the raw recompose; publication fields only |

Dark is the default because the distribution is dark-first: the root `style.json` is the dark style, the site opens dark, and the light style is the explicit alternative. Both styles are generated by [`scripts/style.js`](../scripts/style.js) from `build/style/style.json`, the raw output of `style-tools recompose`.

The theme engine lives in [`scripts/lib/theme.js`](../scripts/lib/theme.js), with colour parsing and contrast helpers in [`scripts/lib/colour.js`](../scripts/lib/colour.js). The detailed rule schema, token resolution, alpha behaviour, expression walking and strict-mode semantics are documented in [`themes/README.md`](../themes/README.md); this page explains how the system is wired into the build, site and screenshots.

## The light contract

[`createLightStyle`](../scripts/style.js) (`:90`) clones the raw recompose and changes only the publication allowlist:

- `name` → `Basemap Light`
- `sprite` → `https://www.ogis.org/basemap/sprite-light`
- `glyphs` → the published font URL
- `sources.openmaptiles.url` → the OpenFreeMap TileJSON URL
- `sources.openmaptiles.attribution` → the required attribution
- `metadata['ogis:theme']` → `light` and `metadata['ogis:upstreamCommit']` → the locked upstream commit

[`validateStyles`](../scripts/style.js) (`:151`) asserts that the light layers are identical to the raw recompose and that no field outside that allowlist changed. Light therefore follows upstream cartography exactly; any future upstream layer or colour appears in the light style without a local rule.

## The dark contract

[`createDarkStyle`](../scripts/style.js) (`:95`) starts from the light clone and applies `themes/dark/theme.json` through `applyTheme`. The engine:

- walks only the allowlisted colour paint properties (`background-color`, `fill-color`, `fill-outline-color`, `line-color`, `icon-color`, `icon-halo-color`, `text-color`, `text-halo-color`);
- evaluates rules in array order, first match wins;
- supports exact layer ids and `*` globs, optional `from` matching and `@token` targets;
- preserves the original alpha by default, multiplying it by any target alpha;
- runs in strict mode by default, rejecting unknown tokens, invalid colours, unknown rule keys, invalid properties and malformed values at compile time, and collecting every unmatched style colour literal at apply time.

Validation then proves that dark is exactly the light style with the theme transformations applied, and that it changed no field other than its name, sprite and metadata ([`scripts/style.js:151-221`](../scripts/style.js)).

> [!IMPORTANT]
> Strict mode is the safety net for upstream changes. When a sync introduces a new colour literal in a themed layer or property, the build fails with the layer, property and literal listed until a deliberate rule is added. Do not disable strict mode to make a build pass.

## Theme data

[`themes/dark/theme.json`](../themes/dark/theme.json) contains the dark tokens and rules. Its base colours come from the Open GIS branding palette: near-black green surfaces, light ink and heading text, muted secondary labels, accent green, orange for major roads and disputed edges, note blue for water and transport labels, and cream for icon glyphs. Map-specific tints for water, vegetation, ground, built-up areas, roads, rail and boundaries are derived from the same greens, blacks and mineral tones so the map reads as a coherent dark surface rather than an inverted light map.

The token groups and the full rule list are maintained in the theme file; [`themes/README.md`](../themes/README.md) documents their meaning and the schema. The colour helpers expose `parseColour`, `tryParseColour`, `canonicalColour`, `formatColour`, `compositeColour`, `relativeLuminance` and `contrastRatio` for tests and tooling.

## Icon palettes

The map theme is not the icon palette. The theme recolours style-layer paint properties; the icon palettes recolour the primary fill baked into selected POI SVG icons before the sprites are built.

- [`palette.json`](../palette.json) — light identity palette. Every target colour equals its source fill, so its staged icons are byte-identical to the vendor SVGs.
- [`themes/dark/palette.json`](../themes/dark/palette.json) — dark palette. Same roles, source mapping, overrides and preserved colours; contrast-tuned target colours derived from the Open GIS branding palette.

[`scripts/palette.js`](../scripts/palette.js) stages either palette with `--theme light|dark --apply` into `build/light/icons` or `build/dark/icons`. The full build stages both, and publishes the dark tree to `icons/` and the light tree to `icons-light/`. The generated app data carries the light palette at the top level and the dark palette under `themes.dark`; the homepage consumes both. See [5.palette.md](5.palette.md) for the role table, contrast measurements and palette workflow.

## Build and publish

[`scripts/build.sh`](../scripts/build.sh) wires the pieces together:

1. Stage both icon palettes.
2. Run one Docker recompose to produce the raw style.
3. Build four sprites: dark `sprite` / `sprite@2x` and light `sprite-light` / `sprite-light@2x`.
4. Run [`scripts/style.js`](../scripts/style.js) to write `build/style/style-dark.json` and `style-light.json`, then validate the pair and the sprite files.
5. Publish `style.json` (dark), `style-light.json`, both sprite sets, `icons/` and `icons-light/`.
6. Merge the font stacks referenced by either style into the shared `fonts/`.
7. Run `scripts/site-build.js`, which copies both styles and their assets into `.output/public` and validates them.

CI has no Docker. The workflows use the committed artefacts, run `npm run upstream:verify`, check the generated palette data, build the site and run both test suites. They do not regenerate the styles or sprites.

> [!IMPORTANT]
> The two styles, both sprite sets, both icon trees and the shared fonts are one deployment unit. The live site serves Basemap Dark as the default at `/basemap/style.json` and Basemap Light at `/basemap/style-light.json`, with both asset sets live; a rebuild must deploy the whole `.output/public`.

## Deployment

Deploy the complete `.output/public` artefact. It contains `style.json` (dark, default), `style-light.json`, both sprite sets, `icons/`, `icons-light/` and the shared `fonts/`. The live deployment serves both styles and both asset sets; a rebuild must publish the whole artefact because publishing one style without its matching sprite or icon tree leaves that style's `sprite` and `icon-image` URLs broken. The Pages workflow uploads the complete `.output/public`.

## Site and screenshots

The site is dark-first:

- The document starts with `data-theme="dark"` and the dark token set; light is an explicit override.
- `?theme=light|dark` selects the initial theme and defaults to dark.
- The **Dark / Light** toggle swaps the site tokens and the map style together, preserving the camera across `map.setStyle`.
- `?style=` overrides the map style entirely and stays fixed when the site palette switches.
- The inspector edits the active palette; **Reset role** restores that palette's generated colour and **Export palette** downloads its current document.
- MapLibre's zoom/compass and attribution controls are themed through the same tokens in both modes.

[`scripts/screenshot.js`](../scripts/screenshot.js) mirrors the same model: `--theme dark|light` selects `./style.json` or `./style-light.json`, localises the matching sprite and glyph URLs into `screenshot-style.json` or `screenshot-light-style.json`, and passes the theme to the page. The end-to-end test server serves those localised styles in memory. See [6.site.md](6.site.md) and [4.screenshots.md](4.screenshots.md).

## Maintenance

### Adding or changing a map-theme rule

1. Apply the theme to the raw or published style, or run the theme tests. A strict failure lists each unmatched layer, property and literal.
2. Add a token if the colour is reused, or a literal if it is a one-off.
3. Place the rule before any broader rule that would otherwise catch the same layer and property.
4. Run `npm test`, then `./scripts/build.sh` to republish both styles.

### Changing a token

Edit the token in `themes/dark/theme.json`, then run the full build. Tokens are resolved at compile time; an unknown `@token` reference fails the build. If a token change alters a documented contrast pair, update the palette or theme documentation alongside it.

### Changing an icon palette

Edit the matching palette source, then run the full build so the staged icon tree and sprite are regenerated. A light palette change updates `icons-light/` and `sprite-light.*`; a dark change updates `icons/` and `sprite.*`. Run `npm run palette:data` when only the app data needs refreshing, or `npm run site:build` when no map artefact changed.

### Adding a theme

The engine is theme-agnostic: a theme is a JSON document with `version`, `name`, `tokens` and `rules`. A new published theme also needs build and site wiring — an output definition in `scripts/style.js`, its icon tree and sprite in `scripts/build.sh` (reusing an existing palette where appropriate), publication and validation in `scripts/site-build.js`, and a way for the site and screenshot harness to select it. Plan those changes together so the deployment still ships a complete style and asset set.

### Upstream sync

`npm run upstream:sync` replaces the vendored mirror, so reapply local cartography edits afterwards. Then run the full build. Strict mode surfaces any new colour literal that needs a rule; the light style continues to follow upstream without changes. Both CI workflows run `npm run upstream:verify` offline after `npm test`.
