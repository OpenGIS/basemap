# Icon Palette

> How the icon colours are defined, selected by the POI style, published for both themes, and changed.

## Overview

Every source icon is a pre-coloured SVG. MapLibre selects an icon by name from a feature's `class` or `subclass`; it does not tint the image. The colour is part of the SVG itself — usually a `fill` attribute on a `<path>` (for example [`camping.svg:2`](../vendor/openmaptiles/style/icons/camping.svg)), sometimes an inline `style="fill:#..."` (for example [`chemist.svg:39`](../vendor/openmaptiles/style/icons/chemist.svg)).

Two icon palettes are published with the distribution:

- The root [`palette.json`](../palette.json) is the light palette. It is the upstream identity: every target colour equals its source fill, so staging reproduces the vendor SVGs byte for byte. Its icons are published to `icons-light/` and its sprite to `sprite-light.*`.
- [`themes/dark/palette.json`](../themes/dark/palette.json) is the dark palette. It keeps the same roles and source mapping and changes only the target colours, anchored to the Open GIS branding palette. Its icons are published to `icons/` and its sprite to `sprite.*`.

The dark map theme in [`themes/dark/theme.json`](../themes/dark/theme.json) is separate: it controls style-layer colours, not the fills baked into the POI SVGs. A map theme and an icon palette are edited and rebuilt independently, although both are produced by the same full build.

[`scripts/build.sh`](../scripts/build.sh) stages both icon trees before Docker ([`scripts/build.sh:49-52`](../scripts/build.sh)); the container mounts them at `/light-icons` and `/dark-icons`, and `spreet` builds both sprite sets ([`scripts/build.sh:54-66`](../scripts/build.sh)). The vendor SVG tree stays pristine.

The sprite is a raster PNG, not an SDF atlas, so `icon-color` and `icon-halo-*` in the style are inert for these icons — even where they are set, as in the Shop and Health layers (`vendor/openmaptiles/layers/poi/style.json:101`, `:1131`).

> [!NOTE]
> Some SVGs carry both a `fill` attribute and an inline `style` fill. The style wins, and the recolourer follows the same precedence (`scripts/lib/recolour.js:249-254`). `books.svg` is the notable case: an obsolete `fill="#734A08"` attribute is overridden by `style="fill:#ac39ac"` (`vendor/openmaptiles/style/icons/books.svg:53-56`), so the icon renders purple. Always check the effective fill before changing a colour.

## Light palette

The light role ids and target colours live in [`palette.json`](../palette.json); `sourceColors` map the original vendor fills to a role, `overrides` reassign individual icons, and `preserve` lists colours that are never recoloured. Edit them directly, or use the homepage [palette inspector](https://www.ogis.org/basemap/) in **Light** mode (after the dual-style deployment, or in a local build) to preview role changes and export a `palette.json` containing the current colours. Browser edits are live only; [6.site.md](6.site.md) covers the inspector and the persistence workflow. The dark palette uses the same roles and schema; see [Light and dark palettes](#light-and-dark-palettes).

The groups below are a cartographic convention, not a strict class-to-colour rule — see [Palette quirks](#palette-quirks).

## Light and dark palettes

Both icon palette documents use the same schema:

- [`palette.json`](../palette.json) is the light palette and the upstream identity. Each role's target colour equals its `sourceColors` fill, so staging reproduces the vendor SVGs byte for byte.
- [`themes/dark/palette.json`](../themes/dark/palette.json) is the dark palette. It keeps the same roles, labels, orders, source fills, `preserve` and `overrides` as the light palette and changes only the target colours, anchored to the Open GIS branding palette.

| Role | Light | Dark | Dark contrast on `#000b00` |
| --- | --- | --- | --- |
| `transport` | `#0092DA` | `#79C0FF` | 10.30:1 |
| `food` | `#C77400` | `#DC8F4E` | 7.71:1 |
| `health` | `#BF0000` | `#F85149` | 5.98:1 |
| `shops` | `#AC39AC` | `#E879F9` | 8.14:1 |
| `public` | `#734A08` | `#D29922` | 7.94:1 |
| `infrastructure` | `#666666` | `#9BB0A3` | 8.72:1 |
| `barriers` | `#3F3F3F` | `#C9D1D9` | 12.98:1 |
| `leisure` | `#2F6133` | `#5CF05C` | 13.43:1 |
| `sport` | `#008C0D` | `#3FB950` | 7.89:1 |
| `terminals` | `#8461C4` | `#A371F7` | 5.98:1 |
| `worship` | `#000000` | `#EEEEEE` | 17.27:1 |

Contrast is the WCAG relative-luminance ratio computed by `contrastRatio` in [`scripts/lib/colour.js`](../scripts/lib/colour.js), measured against the dark branding background `#000b00`. Every dark role clears the 3:1 floor for non-text UI graphics; the current values range from 5.98:1 to 17.27:1.

Theme-specific staging writes to separate directories:

| Command | Palette | Default output |
| --- | --- | --- |
| `node scripts/palette.js --theme light --apply` | `palette.json` | `build/light/icons` |
| `node scripts/palette.js --theme dark --apply` | `themes/dark/palette.json` | `build/dark/icons` |
| `node scripts/palette.js --apply` | `palette.json` | `build/icons` (ad-hoc; not used by the build) |

`--summary` is the default and accepts `--theme` too. `--theme` and `--palette` cannot be combined, and unknown theme names fail. The light staging reports 0 recoloured and is byte-identical to `vendor/openmaptiles/style/icons`. The dark staging recolours only the selected POI icons whose fills map to the palette; every non-POI icon is copied byte-identically.

The full build stages both palettes, then publishes the dark tree to root `icons/` and the light tree to root `icons-light/` ([`scripts/build.sh:100-120`](../scripts/build.sh)). The matching sprites are `sprite.*` for dark and `sprite-light.*` for light. The generated app data also carries the dark palette under `themes.dark`, which the homepage uses in dark mode.

## How icons are selected

The POI style (`vendor/openmaptiles/layers/poi/style.json`) drives icon choice from the feature's `class` and `subclass`:

- Most symbol layers use `"icon-image": "{subclass}"` — Food (`:650`), Public (`:736`), Cultural (`:823`), Transport (`:976`), Accommodation (`:1306`), Place of worship (`:1380`), Bus station (`:1537`) and Zoo (`:1908`).
- Health uses `"icon-image": "{class}"` (`:1086`).
- A few layers hard-code a sprite name: ferry (`:572`), camping (`:1233`), bus stop (`:1457`) and train (`:1754`).
- The Shop layer resolves the subclass image, then the class image, then a `dot` fallback (`:36-60`); there is no `dot.svg` in the source icon set, so that final fallback produces no icon.

Class and subclass definitions live in `vendor/openmaptiles/layers/poi/poi.yaml` — the `shop` class at `:19`, `bar` including `nightclub` at `:81-82`, `car` including `car_repair` and `car_parts` at `:85-86`, and `library` including `books` and `library` at `:65-66`.

## Palette quirks

- **Pharmacy is red, chemist is purple.** `amenity=pharmacy` gets class `pharmacy`, which the Health layer renders with `pharmacy.svg` (`#BF0000`). `shop=chemist` gets class `shop`, subclass `chemist`, which the Shop layer renders with `chemist.svg` (`#AC39AC`). The two tags are not interchangeable.
- **Class boundaries do not guarantee colour.** `car_repair` and `car_parts` sit in the `car` class (Transport) but use purple SVGs; `nightclub` sits in the `bar` class (Food) but uses a brown SVG. `books` and `library` are library-related, but `books.svg` renders purple while `library.svg` is brown; the Cultural and Public filters deliberately exclude `books`, leaving it to the Shop layer.
- **Some icons are in the sprite but unused.** `waterfall`, `fountain`, `saddle` and `doctors` are rasterised into both sprites, but no current layer selects them. Only selected POI icons are recoloured, so they stay at their baked colours in both palettes. If a layer starts referencing one, it enters the recolour set and needs a palette role through `sourceColors` or an `overrides` entry; `doctors` already maps to health, while the other three have symbolic colours outside the main palette.
- **White is often a clip-path background, not a palette group.** White is common in the source SVGs, but it often appears only inside clip paths rather than as visible detail (for example `hospital` and `picnic`). `gate` is a clear visible white fill behind its dark grey bars. The hex in the table is the dominant visible fill.

## Changing a colour

To try a change in the browser first, open the [homepage palette inspector](https://www.ogis.org/basemap/) after the dual-style deployment, or use a local build, choose **Dark** or **Light**, turn on **Inspect POIs**, click a POI and edit its role colour. The inspector applies the colour to every icon in that role live on the map; **Export palette** downloads a `palette.json` containing the active palette's current role colours. Live edits are never written to disk — to make them permanent, update the appropriate palette source and rebuild or restage as described below.

1. Edit [`palette.json`](../palette.json) for the light palette, or [`themes/dark/palette.json`](../themes/dark/palette.json) for the dark palette: change the role's `color`; use `sourceColors` to map a vendor fill to the role, `overrides` to move an individual icon, and `preserve` for colours that must never change. The dark palette keeps the light role ids, labels, orders and source fills and changes only the target colours. A palette whose target colours all equal their source fills is an identity mapping, and the staged output is byte-identical to the vendor tree.
2. To stage icons without building the map, run `node scripts/palette.js --theme light --apply` (writes `build/light/icons`) or `node scripts/palette.js --theme dark --apply` (writes `build/dark/icons`). `--summary` is the default and also accepts `--theme`; `--theme` and `--palette` cannot be combined.
3. Run `./scripts/build.sh` for the published map artefacts. It stages both palettes, runs one Docker recompose, builds both sprite sets and generates both styles ([`scripts/build.sh:49-98`](../scripts/build.sh)). The published `icons/` files are copied from `build/dark/icons` and `icons-light/` from `build/light/icons`; stale icons are removed ([`scripts/build.sh:100-120`](../scripts/build.sh)).
4. To rebuild the site without the map build, run `npm run site:build`; it regenerates `app/assets/data`, runs Nuxt generate, copies both styles and their assets and validates `.output/public` (see [6.site.md](6.site.md)). The full `./scripts/build.sh` already ends with this step.
5. Commit the regenerated map artefacts (`icons/`, `icons-light/`, both sprite sets and both styles) together with the generated app data in `app/assets/data/`. Do not commit `.output/public`; GitHub Actions deploys the site on a push to `master`.
6. Check the result on the homepage inspector in the matching theme, or in any MapLibre map loading `style.json` or `style-light.json`.

Editing the vendor SVGs under `vendor/openmaptiles/style/icons/` is only for changing the source artwork, not the target palette. Changing the artwork changes the source fills that `sourceColors` map from. The mirror is replaced by `npm run upstream:sync`, so reapply artwork edits afterwards.

> [!WARNING]
> Root `icons/`, `icons-light/` and both sprite sets are generated. The next `./scripts/build.sh` overwrites them from the staged directories, which are themselves regenerated from the vendor tree and the two palettes; do not edit the published copies directly. The same applies to `style.json` and `style-light.json`, which are regenerated from the vendored layer styles. Do not try to recolour these icons with `icon-color` or `icon-halo-*` in the POI style — the sprite is raster, not SDF, so those properties are ignored.
