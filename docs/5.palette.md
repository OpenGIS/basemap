# Icon Palette

> How the icon colours are defined, selected by the POI style, and changed.

## Overview

Every source icon is a pre-coloured SVG. MapLibre selects an icon by name from a feature's `class` or `subclass`; it does not tint the image. The colour is part of the SVG itself — usually a `fill` attribute on a `<path>` (for example [`camping.svg:2`](../vendor/openmaptiles/style/icons/camping.svg)), sometimes an inline `style="fill:#..."` (for example [`chemist.svg:39`](../vendor/openmaptiles/style/icons/chemist.svg)).

[`palette.json`](../palette.json) is the editable target palette. It defines the palette roles, the source fills that map to each role, per-icon overrides and colours to preserve. [`scripts/build.sh`](../scripts/build.sh) stages a recoloured copy of the POI icons in `build/icons` before Docker ([`scripts/build.sh:24-25`](../scripts/build.sh)); the container mounts that directory at `/style/icons`, and `spreet` builds the sprite from the staged copy ([`scripts/build.sh:27-35`](../scripts/build.sh)). The vendor SVG tree stays pristine. When every target colour equals its source fill, the staged output is byte-identical to the vendor tree.

The sprite is a raster PNG, not an SDF atlas, so `icon-color` and `icon-halo-*` in the style are inert for these icons — even where they are set, as in the Shop and Health layers (`vendor/openmaptiles/layers/poi/style.json:76`, `:1113`).

> [!NOTE]
> Some SVGs carry both a `fill` attribute and an inline `style` fill. The style wins, and the recolourer follows the same precedence (`scripts/lib/recolour.js:249-254`). `books.svg` is the notable case: an obsolete `fill="#734A08"` attribute is overridden by `style="fill:#ac39ac"` (`vendor/openmaptiles/style/icons/books.svg:53-56`), so the icon renders purple. Always check the effective fill before changing a colour.

## Palette

Role ids and target colours live in [`palette.json`](../palette.json); `sourceColors` map the original vendor fills to a role, `overrides` reassign individual icons, and `preserve` lists colours that are never recoloured. Edit them directly, or use the homepage [palette inspector](https://www.ogis.org/basemap/) to preview role changes and export a `palette.json` containing the current colours. Browser edits are live only; [6.site.md](6.site.md) covers the inspector and the persistence workflow.

The groups below are a cartographic convention, not a strict class-to-colour rule — see [Palette quirks](#palette-quirks).

## How icons are selected

The POI style (`vendor/openmaptiles/layers/poi/style.json`) drives icon choice from the feature's `class` and `subclass`:

- Most symbol layers use `"icon-image": "{subclass}"` — Food (`:635`), Public (`:713`), Cultural (`:799`), Transport (`:953`), Accommodation (`:1291`), Place of worship (`:1365`), Bus station (`:1512`) and Zoo (`:1883`).
- Health uses `"icon-image": "{class}"` (`:1068`).
- A few layers hard-code a sprite name: ferry (`:557`), camping (`:1218`), bus stop (`:1437`) and train (`:1734`).
- The Shop layer resolves the subclass image, then the class image, then a `dot` fallback (`:11-31`); there is no `dot.svg` in the source icon set, so that final fallback produces no icon.

Class and subclass definitions live in `vendor/openmaptiles/layers/poi/poi.yaml` — the `shop` class at `:19`, `bar` including `nightclub` at `:81-82`, `car` including `car_repair` and `car_parts` at `:85-86`, and `library` including `books` and `library` at `:65-66`.

## Palette quirks

- **Pharmacy is red, chemist is purple.** `amenity=pharmacy` gets class `pharmacy`, which the Health layer renders with `pharmacy.svg` (`#BF0000`). `shop=chemist` gets class `shop`, subclass `chemist`, which the Shop layer renders with `chemist.svg` (`#AC39AC`). The two tags are not interchangeable.
- **Class boundaries do not guarantee colour.** `car_repair` and `car_parts` sit in the `car` class (Transport) but use purple SVGs; `nightclub` sits in the `bar` class (Food) but uses a brown SVG. `books` and `library` are library-related, but `books.svg` renders purple while `library.svg` is brown; the Cultural and Public filters deliberately exclude `books`, leaving it to the Shop layer.
- **Some icons are in the sprite but unused.** `waterfall`, `fountain`, `saddle` and `doctors` are rasterised into the sprite, but no current layer selects them. Only selected POI icons are recoloured, so they stay at their baked colours. If a layer starts referencing one, it enters the recolour set and needs a palette role through `sourceColors` or an `overrides` entry; `doctors` already maps to health, while the other three have symbolic colours outside the main palette.
- **White is often a clip-path background, not a palette group.** White is common in the source SVGs, but it often appears only inside clip paths rather than as visible detail (for example `hospital` and `picnic`). `gate` is a clear visible white fill behind its dark grey bars. The hex in the table is the dominant visible fill.

## Changing a colour

To try a change in the browser first, open the [homepage palette inspector](https://www.ogis.org/basemap/), turn on **Inspect POIs**, click a POI and edit its role colour. The inspector applies the colour to every icon in that role live on the map; **Export palette** downloads a `palette.json` containing the current role colours. Live edits are never written to disk — to make them permanent, update the root palette source and run the build below.

1. Edit [`palette.json`](../palette.json): change the role's `color`; use `sourceColors` to map a vendor fill to the role, `overrides` to move an individual icon, and `preserve` for colours that must never change. A palette whose target colours all equal their source fills is an identity mapping, and the staged output is byte-identical to the vendor tree.
2. Run `./scripts/build.sh` for the map artefacts. It runs `node scripts/palette.js --apply` (`npm run palette:apply`), which writes the recoloured copy to `build/icons` ([`scripts/build.sh:25`](../scripts/build.sh)); Docker recomposes the style and `spreet` builds the sprite from those staged icons ([`scripts/build.sh:27-35`](../scripts/build.sh)). The published `icons/` files are copied from `build/icons`, and stale icons are removed ([`scripts/build.sh:51-64`](../scripts/build.sh)).
3. To rebuild the site without the map build, run `npm run site:build`; it regenerates `app/assets/data`, runs Nuxt generate, copies the root map artefacts and validates `.output/public` (see [6.site.md](6.site.md)). The full `./scripts/build.sh` already ends with this step.
4. Commit the regenerated map artefacts (`icons/`, sprites and any changed `style.json`) together with the generated app data in `app/assets/data/`. Do not commit `.output/public`; GitHub Actions deploys the site on a push to `master`.
5. Check the result on the homepage inspector or in any MapLibre map loading `style.json`.

Editing the vendor SVGs under `vendor/openmaptiles/style/icons/` is only for changing the source artwork, not the target palette. Changing the artwork changes the source fills that `sourceColors` map from.

> [!WARNING]
> Root `icons/` and the sprite files are generated. The next `./scripts/build.sh` overwrites them from `build/icons`, which is itself regenerated from the vendor tree and `palette.json`; do not edit the published copies directly. The same applies to `style.json`, which is regenerated from the vendored layer styles. Do not try to recolour these icons with `icon-color` or `icon-halo-*` in the POI style — the sprite is raster, not SDF, so those properties are ignored.
