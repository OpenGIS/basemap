# Site and Palette Inspector

> How the single Nuxt site serves the full-screen basemap and live palette inspector, and how its palette data and Pages artefact are produced.

## Overview

The repository is one root Nuxt 4.3.1 project. It publishes one consumer-facing route under the base path `/basemap/`:

| Route | Source | Purpose |
| --- | --- | --- |
| `/` | [`app/pages/index.vue`](../app/pages/index.vue) | Full-screen MapLibre basemap with the Open GIS overlay and POI palette inspector |

The route is client-only: `ssr: false` disables server rendering ([`nuxt.config.mjs:9`](../nuxt.config.mjs)). Nuxt writes build assets to `nuxt-assets/` rather than the default `/_nuxt/` ([`nuxt.config.mjs:15`](../nuxt.config.mjs)), and MapLibre GL is installed from npm and self-hosted in the site bundle ([`package.json`](../package.json), [`app/pages/index.vue:2-3`](../app/pages/index.vue)). The page title is `Basemap — Open GIS` ([`app/pages/index.vue:30-32`](../app/pages/index.vue)); the Nuxt head supplies the `en-GB` language, a description naming a basemap with a live palette inspector, the colour scheme and the favicon ([`nuxt.config.mjs:13-39`](../nuxt.config.mjs)).

The development server binds to `127.0.0.1` and runs on port 11100 ([`nuxt.config.mjs:42-44`](../nuxt.config.mjs), [`package.json:6`](../package.json)). A dev-only Vite middleware serves the root `style.json` at `/basemap/style.json` ([`nuxt.config.mjs:57-80`](../nuxt.config.mjs)), so the homepage can load the local map data without running a site build first.

## The Nuxt app

- [`app/app.vue`](../app/app.vue) is the shell and renders `<NuxtPage />`.
- [`app/pages/index.vue`](../app/pages/index.vue) is the homepage: a full-screen MapLibre map, the overlay, the POI inspector and the live role-colour updates.
- [`app/utils/mapState.js`](../app/utils/mapState.js) parses and formats the camera hash and provides the legacy query fallback.
- [`app/utils/mapFeatures.js`](../app/utils/mapFeatures.js) resolves a clicked map feature to its palette icon, class and role.
- [`app/utils/svgImage.js`](../app/utils/svgImage.js) rasterises a recoloured SVG template to `ImageData` at the map image's exact pixel size.
- [`app/utils/colour.js`](../app/utils/colour.js) normalises hex values, substitutes `__PALETTE_ROLE__` and builds the exported palette document.
- [`app/assets/data/`](../app/assets/data/) holds generated palette data. Do not hand-edit it; regenerate it with `npm run palette:data`.
- [`app/assets/scss/`](../app/assets/scss/) holds the Open GIS design tokens (`_tokens.scss`) and homepage overlay/inspector styles (`_home.scss`).
- [`app/assets/branding/`](../app/assets/branding/) and [`public/branding/`](../public/branding/) hold build-time and static branding assets.

## Overlay and inspector

The homepage renders the map full-screen behind a fixed, pointer-transparent overlay; the brand panel and inspector re-enable pointer events so they stay interactive over the map ([`app/assets/scss/_home.scss`](../app/assets/scss/_home.scss)).

The brand panel carries the Open GIS logo and wordmark, the `Basemap` title, a short description, the **Inspect POIs** toggle, the **Export palette** button and the live camera readout ([`app/pages/index.vue:420-459`](../app/pages/index.vue)). The readout shows centre latitude/longitude, zoom, pitch and bearing and is updated on every `move`.

**Inspect POIs** is a pressed-state toggle. Turning it on sets a crosshair cursor; turning it off closes the inspector ([`app/pages/index.vue:232-238`](../app/pages/index.vue)). While it is active, a map click queries rendered features on the non-text palette layers and resolves the first matching feature through [`resolveFeature`](../app/utils/mapFeatures.js) (`:41`). That helper evaluates the layer's `icon-image` expression — subclass, class, literal or `coalesce` — finds the icon in the generated palette data and returns its role, class, layer and display name. If no palette POI is found, the overlay shows a short hint.

The inspector shows:

- an icon preview rendered from the generated SVG template with the current role colour;
- the POI name (falling back to the icon name) and its subclass/class;
- the map layer and palette role;
- a colour picker, a hex field and a **Reset role** button;
- a close control, plus a selection marker on the map.

Editing the colour validates the hex with [`normaliseHex`](../app/utils/colour.js) (`:5`), stores the new colour against the role and applies it to every icon in that role. **Reset role** restores the colour from the generated palette data.

### Export and persistence

**Export palette** builds a palette document from the generated source and the current role colours, then downloads it as `palette.json` ([`app/pages/index.vue:261-273`](../app/pages/index.vue), [`buildPaletteDocument`](../app/utils/colour.js) (`:33`)). The document preserves the source structure — roles, `sourceColors`, `preserve` and `overrides` — while replacing each role's `color` with the live value.

Browser edits are live only. Nothing is written to disk or sent to a server, and a reload restores the generated colours. To persist a change, replace the root [`palette.json`](../palette.json) with the exported document and run the map build — `./scripts/build.sh`, which stages the icons (the same step as `npm run palette:apply`), rebuilds the style and sprite, and finishes with the site build. Use `npm run site:build` when only the app data or site code changed. See [5.palette.md](5.palette.md) and [2.build.md](2.build.md).

## Hash camera state

Camera state uses the OSM-style hash `#map=zoom/lat/lng/pitch/bearing`, matching www.ogis.app. The defaults are London Paddington (`51.5154, -0.1755`) at zoom 17 ([`app/utils/mapState.js:1-7`](../app/utils/mapState.js)).

- [`parseMapHash`](../app/utils/mapState.js) (`:16`) accepts exactly five numeric segments.
- [`formatMapHash`](../app/utils/mapState.js) (`:33`) writes latitude/longitude with six decimals and rounds zoom, pitch and bearing to integers.
- [`readMapState`](../app/utils/mapState.js) (`:53`) prefers a valid hash and falls back to the legacy `lat`, `lng`, `zoom`, `pitch` and `rotation` query parameters when the hash is absent or invalid.

On `moveend`, the page writes the current camera back to the hash with `history.replaceState`, preserving the query string. A `hashchange` listener jumps the map to the new state ([`app/pages/index.vue:328-355`](../app/pages/index.vue)). Query parameters remain for `width`, `height`, `style` and `quality`; see [4.screenshots.md](4.screenshots.md) for the full URL API.

## Palette data flow

There is one editable palette source: [`palette.json`](../palette.json) at the repository root. Everything the homepage inspector displays is derived from it.

1. **Model.** [`scripts/lib/palette.js`](../scripts/lib/palette.js) builds the palette model from `palette.json`, the vendored POI schema, mapping and style, `sprite.json` and the source SVGs (`buildModel` at [`scripts/lib/palette.js:491`](../scripts/lib/palette.js)). It resolves each icon's primary fill to a role through `sourceColors`, then applies `overrides` ([`scripts/lib/palette.js:721-775`](../scripts/lib/palette.js)).
2. **App data.** [`scripts/palette-data.js`](../scripts/palette-data.js) serialises the model into [`app/assets/data/`](../app/assets/data/) ([`scripts/palette-data.js:390`](../scripts/palette-data.js)):
   - `palette.json` — roles with their icons and classes, the source palette document, missing names, phantoms, layers and summary.
   - `icons.json` — one SVG template per POI icon, with the primary fill replaced by the `__PALETTE_ROLE__` placeholder.
   - `manifest.json` — the inputs hash and file hashes.

   Generation is deterministic. The inputs hash covers `palette.json`, the palette/recolour/data-generator scripts, the POI schema and style files, `sprite.json` and every source SVG ([`scripts/palette-data.js:61`](../scripts/palette-data.js)). `--check` rebuilds the expected data in memory and reports missing or stale files ([`scripts/palette-data.js:462-497`](../scripts/palette-data.js)).

   Icon templates are built by recolouring each primary fill to a sentinel colour, then replacing the sentinel with `__PALETTE_ROLE__` ([`scripts/palette-data.js:333-388`](../scripts/palette-data.js)). The generator rejects source SVGs that already contain the sentinel or placeholder, so the template substitution is unambiguous.
3. **Runtime.** The homepage imports the generated data. It builds a reactive `roleColours` map from the generated roles, uses [`iconDataUri`](../app/utils/colour.js) (`:23`) for the inspector preview, and uses each role's `iconNames` to recolour the map images live. Only the placeholder is replaced; white, preserved and non-primary details stay as they are in the template.

`npm run palette:data` writes the data and `npm run palette:data:check` verifies it is in sync. Both derive the expected data from the root palette source; `--check` then compares it with the generated copies.

## Icon recolour mechanism

MapLibre renders POI icons from the sprite as named images. The generated `icons.json` holds the matching SVG templates, so a role change does not need a new sprite build: the page rewrites the in-memory images and repaints.

For each icon in the edited role, [`updateMapImage`](../app/pages/index.vue) (`:99-123`) applies:

1. Normalises the role hex and checks that the map still has an image and a template for that icon.
2. Reads the current image's exact `data.width` and `data.height` from `map.getImage(name)`.
3. Substitutes every `__PALETTE_ROLE__` placeholder in the SVG template with the hex.
4. Rasterises the SVG to `ImageData` at those exact dimensions with [`svgToImageData`](../app/utils/svgImage.js) (`:10`), which draws the SVG onto a canvas and reads the pixels back.
5. Calls `map.updateImage(name, imageData)` and, once the role's icons are queued and applied, `map.triggerRepaint()`.

Image updates are serialised through a promise queue so rapid colour changes cannot interleave, and `applyRoleImages` only repaints after all icons in the role have been replaced ([`app/pages/index.vue:125-157`](../app/pages/index.vue)). Exact dimensions matter: `updateImage` replaces the sprite frame with the supplied pixels, so reusing the original width and height avoids resampling and keeps icons aligned with their rendered size.

On the first `idle`, `applyAllImages` applies every role's current colour to its icons before setting `body[data-map-ready]` ([`app/pages/index.vue:130-142`](../app/pages/index.vue), [`app/pages/index.vue:357-390`](../app/pages/index.vue)). This makes the rendered images consistent with the generated palette data even when the sprite already matches the committed role colours.

## Map data

The map data stays at the repository root, where the map build writes it:

- `style.json`
- `sprite.json`, `sprite.png`, `sprite@2x.json` and `sprite@2x.png`
- `icons/`
- `fonts/`

These are committed artefacts produced by [`scripts/build.sh`](../scripts/build.sh) (see [2.build.md](2.build.md)). They are not duplicated inside `app/`.

## Site build

[`scripts/site-build.js`](../scripts/site-build.js) assembles the deployable site in `.output/public`:

1. Regenerates `app/assets/data` with `scripts/palette-data.js`.
2. Runs `npm run generate` (`nuxt generate`).
3. Copies the root map files and directories into `.output/public`, and copies the MapLibre worker files from `node_modules/maplibre-gl/dist` into `nuxt-assets/` ([`scripts/site-build.js:281-324`](../scripts/site-build.js)).
4. Validates the generated `index.html`, local asset paths under `/basemap/`, the required map files, the MapLibre worker files, the `icons/` and `fonts/` directories and the absence of `_nuxt`/`_payload.json` references ([`scripts/site-build.js:192-243`](../scripts/site-build.js)).

The page list contains only `index.html` ([`scripts/site-build.js:27`](../scripts/site-build.js)); the site has no second page to validate. `.output/public` is generated and gitignored. It is never committed; the Pages workflow uploads it as the deployment artefact.

## Local workflow

```bash
npm install
npx playwright install chromium   # screenshots and end-to-end tests
npm run dev
```

`npm run dev` serves the homepage at <http://127.0.0.1:11100/basemap/>.

`npm test` runs the Node suite. `npm run test:e2e:build` builds `.output/public` and runs the Playwright smoke suite; `npm run test:e2e` reuses an existing build. The test server serves the built site at <http://127.0.0.1:11101/basemap/> with a 1200x630 viewport (see [4.screenshots.md](4.screenshots.md)).

After editing `palette.json`, regenerate the data the homepage imports:

```bash
npm run palette:data
npm run palette:data:check
```

To produce the complete deployable site locally:

```bash
npm run site:build
```

This writes `.output/public`, including the Nuxt homepage, the generated palette data and the copied map artefacts. `npm run site:generate` runs only `nuxt generate`; `npm run site:build` is the full artefact build. The screenshot tools and the end-to-end suite require the `.output/public` build, so run `npm run site:build` before `npm run screenshot` or `npm run test:e2e` (see [4.screenshots.md](4.screenshots.md)). For the default style, the screenshot tools rewrite `sprite` and `glyphs` to absolute local URLs in a generated `.output/public/screenshot-style.json`, because MapLibre GL JS 6.5.0 rejects relative sprite URLs.

## Deployment

[`.github/workflows/pages.yml`](../.github/workflows/pages.yml) deploys only the consumer-facing homepage. It runs on pushes to `master` and on manual dispatch. The workflow:

1. Installs dependencies with `npm ci`.
2. Runs `npm test`.
3. Runs `npm run palette:data:check`.
4. Runs `npm run site:build`.
5. Installs Chromium with `npx playwright install --with-deps chromium`.
6. Runs `npm run test:e2e`.
7. Uploads `.output/public` as the Pages artefact and deploys it.

Both suites must pass before the upload; an end-to-end failure blocks deployment because the deploy job depends on the build job.

> [!IMPORTANT]
> In the repository's GitHub Pages settings, set **Source** to **GitHub Actions** once. The workflow uploads `.output/public`; there is no `gh-pages` branch and no generated site output in the repository.

The technical documentation under `docs/` is repository-only. It is not part of `.output/public` and is not published to Pages.

## CI

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on pull requests. It installs dependencies, runs `npm test`, checks the generated palette data with `npm run palette:data:check`, runs `npm run site:build`, installs Chromium with `npx playwright install --with-deps chromium`, and runs `npm run test:e2e`.

The Pages workflow repeats the Node suite, data check, site build, Chromium install and end-to-end suite on `master` pushes before deploying. Neither workflow builds the map with Docker; the map artefacts are committed and the site build copies them. Both workflows install Chromium for the end-to-end suite.

## Tests and attribution

`npm test` runs the Node test suite with `node --test`. It covers the palette model and recolouring, generated palette data, the homepage's colour, map-state and map-feature helpers, and site-build validation. It does not launch a browser.

`npm run test:e2e` runs the Playwright smoke suite against `.output/public`, served by `scripts/test-server.js` at <http://127.0.0.1:11101/basemap/> with a 1200x630 viewport. `npm run test:e2e:build` runs `npm run site:build` first. The suite checks the homepage render and readout, then the inspector's recolour and export flow, without console or page errors. It refreshes the committed `screenshots/home.png` capture and writes a temporary inspector capture to `.opencode/tmp/home-inspector.png`. It requires Chromium (`npx playwright install chromium`).
