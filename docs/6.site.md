# Site and Palette Editor

> How the single Nuxt site serves the map demo and palette editor, and how its palette data and Pages artefact are produced.

## Overview

The repository is one root Nuxt 4.3.1 project. It publishes the consumer-facing map demo and the palette editor from the same codebase, under the base path `/basemap/`:

| Route | Source | Purpose |
| --- | --- | --- |
| `/` | [`app/pages/index.vue`](../app/pages/index.vue) | State-driven MapLibre GL demo |
| `/palette/` | [`app/pages/palette.vue`](../app/pages/palette.vue) | Preview, edit and export the icon palette |

Both routes are client-only: `ssr: false` disables server rendering ([`nuxt.config.mjs:9`](../nuxt.config.mjs)). Nuxt writes build assets to `nuxt-assets/` rather than the default `/_nuxt/` ([`nuxt.config.mjs:15`](../nuxt.config.mjs)), and MapLibre GL is installed from npm and self-hosted in the site bundle ([`package.json`](../package.json), [`app/pages/index.vue:2-3`](../app/pages/index.vue)).

The development server binds to `127.0.0.1` and runs on port 11100 ([`nuxt.config.mjs:42-44`](../nuxt.config.mjs), [`package.json:6`](../package.json)). A dev-only Vite middleware serves the root `style.json` at `/basemap/style.json` ([`nuxt.config.mjs:57-80`](../nuxt.config.mjs)), so the demo can load the local map data without running a site build first.

## The Nuxt app

- [`app/app.vue`](../app/app.vue) is the shell and renders `<NuxtPage />`.
- [`app/pages/index.vue`](../app/pages/index.vue) is the demo. It imports `maplibre-gl` from npm, reads the map state from URL query parameters and exposes the automation signals used by the screenshot tools. See [4.screenshots.md](4.screenshots.md).
- [`app/pages/palette.vue`](../app/pages/palette.vue) is the palette editor. It loads Pico CSS, the Open GIS SCSS layer and the shared palette components.
- [`app/components/`](../app/components/), [`app/composables/`](../app/composables/) and [`app/utils/`](../app/utils/) hold the editor UI, state and colour helpers.
- [`app/assets/scss/`](../app/assets/scss/), [`app/assets/branding/`](../app/assets/branding/) and [`public/branding/`](../public/branding/) hold the theme and branding assets.
- [`app/assets/data/`](../app/assets/data/) holds generated palette data. Do not hand-edit it; regenerate it with `npm run palette:data`.

The palette route is a Nuxt route at `/basemap/palette/`. It is not a separate application or a separate base path.

## Palette data flow

There is one editable palette source: [`palette.json`](../palette.json) at the repository root. Everything the editor displays is derived from it.

1. **Model.** [`scripts/lib/palette.js`](../scripts/lib/palette.js) builds the palette model from `palette.json`, the vendored POI schema, mapping and style, `sprite.json` and the source SVGs (`buildModel` at [`scripts/lib/palette.js:491`](../scripts/lib/palette.js)). It resolves each icon's primary fill to a role through `sourceColors`, then applies `overrides` ([`scripts/lib/palette.js:721-775`](../scripts/lib/palette.js)).
2. **App data.** [`scripts/palette-data.js`](../scripts/palette-data.js) serialises the model into [`app/assets/data/`](../app/assets/data/) ([`scripts/palette-data.js:11`](../scripts/palette-data.js)):
   - `palette.json` — roles, classes, icons, missing names, phantoms, layers and summary.
   - `icons.json` — one SVG template per POI icon, with the primary fill replaced by the `__PALETTE_ROLE__` placeholder.
   - `manifest.json` — the inputs hash and file hashes.

   Generation is deterministic. The inputs hash covers `palette.json`, the palette/recolour/data-generator scripts, the POI schema and style files, `sprite.json` and every source SVG ([`scripts/palette-data.js:17-28`](../scripts/palette-data.js), [`scripts/palette-data.js:52-59`](../scripts/palette-data.js)). `--check` rebuilds the expected data in memory and reports missing or stale files ([`scripts/palette-data.js:462-497`](../scripts/palette-data.js)).

   Icon templates are built by recolouring each primary fill to a sentinel colour, then replacing the sentinel with `__PALETTE_ROLE__` ([`scripts/palette-data.js:333-388`](../scripts/palette-data.js)). The generator rejects source SVGs that already contain the sentinel or placeholder, so the template substitution is unambiguous.
3. **Runtime.** The app imports the generated data. [`app/components/PaletteClassGroup.vue`](../app/components/PaletteClassGroup.vue) substitutes the current role colour for `__PALETTE_ROLE__` and converts the SVG to a data URI ([`app/utils/colour.js:23-31`](../app/utils/colour.js)). Only the placeholder is replaced; white, preserved and non-primary details stay as they are in the template.

`npm run palette:data` writes the data and `npm run palette:data:check` verifies it is in sync. Both derive the expected data from the root palette source; `--check` then compares it with the generated copies.

## Map data

The map data stays at the repository root, where the map build writes it:

- `style.json`
- `sprite.json`, `sprite.png`, `sprite@2x.json` and `sprite@2x.png`
- `icons/`
- `fonts/`

These are committed artefacts produced by [`scripts/build.sh`](../scripts/build.sh) (see [2.build.md](2.build.md)). They are not duplicated inside `app/`.

[`scripts/site-build.js`](../scripts/site-build.js) assembles the deployable site in `.output/public`:

1. Regenerates `app/assets/data` with `scripts/palette-data.js`.
2. Runs `npm run generate` (`nuxt generate`).
3. Copies the root map files and directories into `.output/public`, and copies the MapLibre worker files from `node_modules/maplibre-gl/dist` into `nuxt-assets/` ([`scripts/site-build.js:281-324`](../scripts/site-build.js)).
4. Validates both pages, local asset paths under `/basemap/`, the required map files and the absence of `_nuxt`/`_payload.json` references ([`scripts/site-build.js:192-243`](../scripts/site-build.js)).

`.output/public` is generated and gitignored. It is never committed; the Pages workflow uploads it as the deployment artefact.

## Local workflow

```bash
npm install
npx playwright install chromium   # only needed for screenshots
npm run dev
```

`npm run dev` serves the site at <http://127.0.0.1:11100/basemap/>. The map demo is at `/basemap/` and the palette editor is at `/basemap/palette/`.

After editing `palette.json`, regenerate the data the editor imports:

```bash
npm run palette:data
npm run palette:data:check
```

To produce the complete deployable site locally:

```bash
npm run site:build
```

This writes `.output/public`, including the Nuxt pages, the generated palette data and the copied map artefacts. `npm run site:generate` runs only `nuxt generate`; `npm run site:build` is the full artefact build. The screenshot tools require the `.output/public` build, so run `npm run site:build` before `npm run screenshot` or `npm run screenshot:random` (see [4.screenshots.md](4.screenshots.md)).

## Deployment

[`.github/workflows/pages.yml`](../.github/workflows/pages.yml) deploys only the consumer-facing map and palette site. It runs on pushes to `master` and on manual dispatch. The workflow:

1. Installs dependencies with `npm ci`.
2. Runs `npm test`.
3. Runs `npm run palette:data:check`.
4. Runs `npm run site:build`.
5. Uploads `.output/public` as the Pages artefact and deploys it.

> [!IMPORTANT]
> In the repository's GitHub Pages settings, set **Source** to **GitHub Actions** once. The workflow uploads `.output/public`; there is no `gh-pages` branch and no generated site output in the repository.

The technical documentation under `docs/` is repository-only. It is not part of `.output/public` and is not published to Pages.

## CI

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on pull requests. It installs dependencies, runs `npm test`, checks the generated palette data with `npm run palette:data:check`, and runs `npm run site:build`.

The Pages workflow repeats the tests, data check and site build on `master` pushes before deploying. Neither workflow builds the map with Docker or installs a browser; the map artefacts are committed and the site build copies them.

## Tests and attribution

`npm test` runs the Node test suite with `node --test`. It covers the palette model and recolouring, generated palette data, the editor's colour and filter helpers, and site-build validation. No test launches a browser, so CI needs Node and npm only.

The site includes work from Open GIS branding, Pico CSS, OpenMapTiles and OpenStreetMap. See the root [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md) for the third-party notices and licence terms.
