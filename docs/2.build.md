# Build Pipeline

> How `scripts/build.sh` turns the vendored OpenMapTiles sources into the two published styles, their sprites and icons, the shared fonts and the deployable site.

## Overview

The build reproduces `make build-style` from the vendored upstream OpenMapTiles sources, using the same docker tooling, then derives both published styles from that single recompose, rewrites them to point at the published URLs, publishes both sprite and icon sets, merges the font stacks referenced by either style and assembles the static site.

Pipeline: **dual palette staging → one docker recompose → four sprites → style generation and validation → publish both styles, sprites and icon trees → font merging from both styles → site build**.

| Output | Source | Transform |
| --- | --- | --- |
| Dark style (`style.json`, default) | Raw recompose → light clone | Strict ordered theme from `themes/dark/theme.json` |
| Light style (`style-light.json`) | Raw recompose | Publication fields only; layer tree unchanged |

## Vendor sync

The sources under [`vendor/openmaptiles/`](../vendor/openmaptiles/) are a pristine mirror of a commit of [OpenMapTiles](https://github.com/openmaptiles/openmaptiles) `master`; upstream is the source of truth. The mirror contains only `LICENSE.md`, `layers/`, `openmaptiles.yaml` and `style/`. Provenance lives outside the mirrored tree in [`vendor/openmaptiles.lock.json`](../vendor/openmaptiles.lock.json), and [`vendor/README.md`](../vendor/README.md) documents the layout.

Vendor commands:

```bash
npm run upstream:sync    # resolve master, download it and replace the mirror
npm run upstream:verify  # offline: recompute the manifest and compare it to the lock
npm run upstream:check   # network: fetch the latest master SHA and compare it to the lock
```

`upstream:sync` resolves `master` to a commit SHA through the GitHub API, downloads that commit's tarball, stages only the mirrored paths and atomically replaces the tree before writing the lock. Use `node scripts/sync-upstream.js --sync --ref <sha>` when API resolution is unavailable or rate-limited.

`upstream:verify` is fully offline. It recomputes the deterministic manifest hash and fails on missing files, extra entries (such as `.DS_Store` or a leftover `VENDOR.md`) or a lock mismatch, so CI uses it. Both [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) and [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) run it immediately after `npm test`. `upstream:check` is the explicit network mode for manual or scheduled use; it exits non-zero when upstream `master` has moved past the locked commit.

The lock records the upstream URL, ref, commit SHA, sync time, OpenMapTiles tools version (`7.2`), mirrored paths, file count and a `sha256:` manifest hash.

> [!IMPORTANT]
> Syncing source does not rebuild or republish the styles. The published `style.json`, `style-light.json`, sprites, icons and fonts change only when `./scripts/build.sh` runs.

## 1. Dual palette staging

Before Docker, [`scripts/build.sh`](../scripts/build.sh) stages both icon trees ([`scripts/build.sh:49-52`](../scripts/build.sh)):

```bash
node scripts/palette.js --theme light --apply
node scripts/palette.js --theme dark --apply
```

`--theme light` reads the root light [`palette.json`](../palette.json) and writes `build/light/icons`; `--theme dark` reads [`themes/dark/palette.json`](../themes/dark/palette.json) and writes `build/dark/icons`. Both use the same palette model and recolour pipeline ([`scripts/lib/recolour.js`](../scripts/lib/recolour.js)).

Only selected POI icons are recoloured, and only their primary fill is changed. Inline `style="fill:..."` overrides win over a `fill` attribute; white, preserved and non-primary details are left untouched; non-POI SVGs are copied unchanged. The vendor tree under `vendor/openmaptiles/style/icons/` stays pristine. The light palette is the identity mapping, so its staged output is byte-identical to the vendor tree; the dark palette changes only the target role colours. See [5.palette.md](5.palette.md).

> [!NOTE]
> The unprefixed `node scripts/palette.js --apply` still writes `build/icons` from the root light palette for ad-hoc use, but `scripts/build.sh` uses the two themed directories.

## 2. Docker recompose

[`scripts/build.sh`](../scripts/build.sh) runs the `openmaptiles/openmaptiles-tools:7.2` image with the project root mounted at `/tileset`, `vendor/openmaptiles/style` at `/style`, and the two staged icon trees at `/light-icons` and `/dark-icons` ([`scripts/build.sh:54-66`](../scripts/build.sh)):

```bash
docker run --rm --user="$(id -u):$(id -g)" \
  -v "$ROOT":/tileset \
  -v "$ROOT/vendor/openmaptiles/style":/style \
  -v "$ROOT/build/light/icons":/light-icons \
  -v "$ROOT/build/dark/icons":/dark-icons \
  -w /tileset \
  openmaptiles/openmaptiles-tools:7.2 \
  bash -c 'style-tools recompose vendor/openmaptiles/openmaptiles.yaml build/style/style.json vendor/openmaptiles/style/style-header.json \
    && spreet /dark-icons build/style/sprite \
    && spreet --retina /dark-icons build/style/sprite@2x \
    && spreet /light-icons build/style/sprite-light \
    && spreet --retina /light-icons build/style/sprite-light@2x'
```

- `style-tools recompose` runs **once** and combines the layer styles under `vendor/openmaptiles/layers/*/style.json` with the header (`vendor/openmaptiles/style/style-header.json`) into the raw style at `build/style/style.json`.
- `spreet` builds four sprite sheets: the dark `sprite` and `sprite@2x` from `build/dark/icons`, and the light `sprite-light` and `sprite-light@2x` from `build/light/icons`. The icon bind mounts are separate from the `/style` mount, so `spreet` reads the staged trees rather than the pristine vendor icons.

## 3. Style generation and validation

[`scripts/style.js`](../scripts/style.js) reads the raw recompose and writes both styles ([`scripts/build.sh:68-69`](../scripts/build.sh)):

- **Light** ([`createLightStyle`](../scripts/style.js) `:90`) clones the raw style and changes only the publication fields: name `Basemap Light`, sprite `https://www.ogis.org/basemap/sprite-light`, the glyphs URL, the OpenFreeMap tile URL, the attribution and `metadata['ogis:theme'] = 'light'` plus the upstream commit.
- **Dark** ([`createDarkStyle`](../scripts/style.js) `:95`) clones the light style and applies `themes/dark/theme.json` strictly through [`scripts/lib/theme.js`](../scripts/lib/theme.js). Only allowlisted paint colour properties change; the name becomes `Basemap Dark`, the sprite becomes `https://www.ogis.org/basemap/sprite`, and the metadata records `ogis:theme = 'dark'` and the upstream commit.

The build then runs `node scripts/style.js --validate` and checks that every file in both sprite sets exists and that each sprite JSON is a non-empty object ([`scripts/build.sh:71-88`](../scripts/build.sh)). Validation proves the light layers are identical to the raw recompose, that light changed nothing outside the publication allowlist, that dark is exactly the light style with the strict theme applied, and that dark changed no field other than its name, sprite and metadata.

> [!NOTE]
> URLs use **www.ogis.org** directly because the org's legacy `*.github.io` Pages host 301-redirects to it, and Chrome blocks cross-origin fetches that hit a redirect hop without a CORS header.

## 4. Publish to root

The final map artefacts are copied to the repository root, where they are committed ([`scripts/build.sh:90-98`](../scripts/build.sh)):

- `style.json` — the dark default
- `style-light.json` — the light variant
- `sprite.json`, `sprite.png`, `sprite@2x.json`, `sprite@2x.png`
- `sprite-light.json`, `sprite-light.png`, `sprite-light@2x.json`, `sprite-light@2x.png`

The icon trees are then published ([`scripts/build.sh:100-120`](../scripts/build.sh)):

- `build/dark/icons` → `icons/`
- `build/light/icons` → `icons-light/`

Any icon no longer present in the staged source is removed from the matching root directory during publish, so stale icons do not linger.

These root artefacts are the source for the site build. [`scripts/site-build.js`](../scripts/site-build.js) copies them into `.output/public` for deployment; they are not duplicated in the Nuxt app. `build/` and `.output/` are both gitignored.

## 5. Font merging

[`scripts/merge-fonts.js`](../scripts/merge-fonts.js) pre-merges the comma-joined `text-font` stacks from **both** `style.json` and `style-light.json` ([`scripts/merge-fonts.js:24`](../scripts/merge-fonts.js)) into on-disk comma-named glyph directories under `fonts/`.

MapLibre GL requests glyphs with the `text-font` array joined by commas as the `{fontstack}` URL segment, e.g. `["Open Sans Semibold","Noto Sans Bold"]` → `fonts/Open Sans Semibold,Noto Sans Bold/0-255.pbf`. GitHub Pages is static, so those stacks must be pre-merged at build time:

- For each glyph range, glyphs are merged across the stack's fonts — first font wins per glyph id, missing glyphs are filled from subsequent fonts (e.g. CJK flows from Noto Sans).
- Single-font stacks are served as-is.
- The script is zero-dependency: it implements a minimal reader/writer for the fontnik/Mapbox glyph PBF schema only.
- It is idempotent: merged directories are removed and rewritten on every run.

Result: one shared directory per fontstack referenced by either style, with a PBF file per 256-glyph range.

## 6. Site build

[`scripts/build.sh`](../scripts/build.sh) runs `node scripts/site-build.js` after font merging ([`scripts/build.sh:125-126`](../scripts/build.sh)). The site build:

1. Regenerates `app/assets/data` with [`scripts/palette-data.js`](../scripts/palette-data.js); the generated palette document contains the top-level light data plus `themes.dark.palette` and `themes.dark.colours`.
2. Runs `npm run generate` (`nuxt generate`).
3. Copies both styles, both sprite sets, `icons/`, `icons-light/`, `fonts/` and the MapLibre worker files into `.output/public` ([`scripts/site-build.js:411-446`](../scripts/site-build.js)).
4. Validates the generated `index.html`, local asset paths under `/basemap/`, both style documents, both sprite sets, both icon directories, the shared fonts, the MapLibre worker files and the absence of `_nuxt`/`_payload.json` references ([`scripts/site-build.js:280-346`](../scripts/site-build.js)). It also requires `style.json` to record `ogis:theme = 'dark'` and `style-light.json` to record `ogis:theme = 'light'` ([`scripts/site-build.js:300-307`](../scripts/site-build.js)).

The page list contains only `index.html` ([`scripts/site-build.js:27`](../scripts/site-build.js)). `.output/public` is generated and gitignored. It is not committed; GitHub Actions ([`.github/workflows/pages.yml`](../.github/workflows/pages.yml)) uploads it as the Pages artefact on a push to `master`. The artefact is one deployment unit: both styles, both sprite sets, both icon directories and the shared fonts must ship together. See [6.site.md](6.site.md) for the homepage route, palette data flow and deployment workflow.

## Running the Build

```bash
./scripts/build.sh
```

Requires Docker and Node.js. The style artefacts (`style.json`, `style-light.json`, both sprite sets, both icon trees, fonts) are deterministic and idempotent — re-running the build reproduces them exactly. The end-to-end suite runs separately and needs the Playwright tooling (`npm install` + `npx playwright install chromium`).

To build only the deployable site after the map artefacts exist, run `npm run site:build`; it regenerates the palette data, runs Nuxt generate, copies both styles and their assets into `.output/public` and validates the result.

The build does not run the test suites. Run `npm test` for the Node suite and `npm run test:e2e:build` to build the site and run the Playwright smoke suite (`npm run test:e2e` reuses an existing build); see [4.screenshots.md](4.screenshots.md).

> [!NOTE]
> CI has no Docker. The workflows use the committed map artefacts, run `npm run upstream:verify`, check the generated palette data, build the site and run both test suites. They do not rebuild the styles or sprites.
