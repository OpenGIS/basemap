# Build Pipeline

> How `scripts/build.sh` turns the vendored OpenMapTiles sources into the published map artefacts and the deployable site.

## Overview

The build reproduces `make build-style` from OpenMapTiles v3.16 against the vendored sources, using the same docker tooling, then rewrites the result to point at the published URLs, merges the comma-joined font stacks and assembles the static site.

Pipeline: **palette staging → docker recompose → sprite generation → jq rewrite → publish to root → font merging → site build → random screenshot**.

## 1. Palette staging

Before Docker, [`scripts/build.sh`](../scripts/build.sh) runs `node scripts/palette.js --apply` ([`scripts/build.sh:24-25`](../scripts/build.sh)). This reads the root [`palette.json`](../palette.json), builds the palette model from the vendored POI schema, mapping, style and sprite together with the source SVGs, and writes a recoloured copy of every source icon to `build/icons`.

Only selected POI icons are recoloured, and only their primary fill is changed ([`scripts/lib/recolour.js`](../scripts/lib/recolour.js)). Inline `style="fill:..."` overrides win over a `fill` attribute; white, preserved and non-primary details are left untouched; non-POI SVGs are copied unchanged. The vendor tree under `vendor/openmaptiles/style/icons/` stays pristine. When every target colour equals its source fill, the staged output is byte-identical to the vendor tree.

## 2. Docker recompose

[`scripts/build.sh`](../scripts/build.sh) runs the `openmaptiles/openmaptiles-tools:7.2` image with the project root mounted at `/tileset`, `vendor/openmaptiles/style` mounted at `/style`, and the staged icons mounted at `/style/icons`:

```bash
docker run --rm --user="$(id -u):$(id -g)" \
  -v "$ROOT":/tileset \
  -v "$ROOT/vendor/openmaptiles/style":/style \
  -v "$ROOT/build/icons":/style/icons \
  -w /tileset \
  openmaptiles/openmaptiles-tools:7.2 \
  bash -c 'style-tools recompose vendor/openmaptiles/openmaptiles.yaml build/style/style.json vendor/openmaptiles/style/style-header.json \
    && spreet /style/icons build/style/sprite \
    && spreet --retina /style/icons build/style/sprite@2x'
```

- `style-tools recompose` combines the layer styles under `vendor/openmaptiles/layers/*/style.json` with the header (`vendor/openmaptiles/style/style-header.json`) into a single style at `build/style/style.json`.
- `spreet` builds the sprite sheets from the staged, palette-recoloured SVGs in `build/icons` — `build/style/sprite` (plus `--retina` for `sprite@2x`). The `build/icons` bind mount shadows the vendor icons directory, so `spreet` never reads the pristine source tree.

## 3. jq rewrite

The recomposed style is rewritten with `jq` to point at the published URLs:

- `name` → `"Basemap"`
- `glyphs` → `https://www.ogis.org/basemap/fonts/{fontstack}/{range}.pbf`
- `sprite` → `https://www.ogis.org/basemap/sprite`
- `sources.openmaptiles.url` → `https://tiles.openfreemap.org/planet`
- `sources.attribution.attribution` → OpenFreeMap + © OpenMapTiles + Data from OpenStreetMap

> [!NOTE]
> URLs use **www.ogis.org** directly because the org's legacy `*.github.io` Pages host 301-redirects to it, and Chrome blocks cross-origin fetches that hit a redirect hop without a CORS header.

## 4. Publish to root

The final map artefacts are copied to the repository root, where they are committed ([`scripts/build.sh:50-64`](../scripts/build.sh)):

- `style.json`
- `sprite.json`, `sprite.png`, `sprite@2x.json`, `sprite@2x.png`
- `icons/*.svg`, copied from `build/icons`

The published icon files therefore match the staged palette copy that produced the sprite. Any icon no longer present in `build/icons` is removed from root `icons/` during publish ([`scripts/build.sh:57-64`](../scripts/build.sh)), so stale icons do not linger.

These root artefacts are the source for the site build. [`scripts/site-build.js`](../scripts/site-build.js) copies them into `.output/public` for deployment; they are not duplicated in the Nuxt app. `build/` and `.output/` are both gitignored.

## 5. Font merging

[`scripts/merge-fonts.js`](../scripts/merge-fonts.js) pre-merges the comma-joined `text-font` stacks from `style.json` into on-disk comma-named glyph directories under `fonts/`.

MapLibre GL requests glyphs with the `text-font` array joined by commas as the `{fontstack}` URL segment, e.g. `["Open Sans Semibold","Noto Sans Bold"]` → `fonts/Open Sans Semibold,Noto Sans Bold/0-255.pbf`. GitHub Pages is static, so those stacks must be pre-merged at build time:

- For each glyph range, glyphs are merged across the stack's fonts — first font wins per glyph id, missing glyphs are filled from subsequent fonts (e.g. CJK flows from Noto Sans).
- Single-font stacks are served as-is.
- The script is zero-dependency: it implements a minimal reader/writer for the fontnik/Mapbox glyph PBF schema only.
- It is idempotent: merged directories are removed and rewritten on every run.

Result: one directory per fontstack (single fonts plus merged comma-joined stacks), with a PBF file per 256-glyph range.

## 6. Site build

[`scripts/build.sh`](../scripts/build.sh) runs `node scripts/site-build.js` after font merging and before the random screenshot ([`scripts/build.sh:70-72`](../scripts/build.sh)). The site build:

1. Regenerates `app/assets/data` with [`scripts/palette-data.js`](../scripts/palette-data.js).
2. Runs `npm run generate` (`nuxt generate`).
3. Copies the root map files and directories into `.output/public`, plus the MapLibre worker files from `node_modules/maplibre-gl/dist` into `nuxt-assets/` ([`scripts/site-build.js:281-324`](../scripts/site-build.js)).
4. Validates the generated `index.html`, local asset paths under `/basemap/`, the required map files and the absence of `_nuxt`/`_payload.json` references ([`scripts/site-build.js:192-243`](../scripts/site-build.js)). The page list contains only `index.html` ([`scripts/site-build.js:27`](../scripts/site-build.js)).

`.output/public` is generated and gitignored. It is not committed; GitHub Actions ([`.github/workflows/pages.yml`](../.github/workflows/pages.yml)) uploads it as the Pages artefact on a push to `master`. See [6.site.md](6.site.md) for the homepage route, palette data flow and deployment workflow.

## 7. Random screenshot

The build ends by running [`scripts/random-map.js`](../scripts/random-map.js), which renders a fresh random basemap to `screenshots/random.jpg` at 1200x630 (see [4.screenshots.md](4.screenshots.md)). It picks a random land point anywhere on Earth (Natural Earth 110m polygons, fetched on first run and cached at `build/land-110m.geojson`), then quality-gates the render — re-rolling up to 15 times until the harness's quality score clears the threshold, with zoom biased towards detail (70% of attempts zoom 12–14, 30% zoom 10–12). This artefact is intentionally non-deterministic — every build produces a different map — so the README screenshot stays fresh. The step fails loudly (exit code 1) if land data is unavailable or no render clears the threshold — the build fails rather than falling back to a curated render. Commit the regenerated `screenshots/random.jpg` with the other build artefacts.

> [!NOTE]
> The build needs network access on first run to fetch the land polygons (the tiles already need network). Subsequent runs use the cached copy in `build/` and work offline.

## Running the Build

```bash
./scripts/build.sh
```

Requires Docker, Node.js and `jq`. The final random-screenshot step also needs the Playwright tooling (`npm install` + `npx playwright install chromium`); the same Chromium binary is used by the end-to-end suite. The style artefacts (`style.json`, sprites, icons, fonts) are deterministic and idempotent — re-running the build reproduces them exactly. The one exception is `screenshots/random.jpg`, which is intentionally re-rendered as a random map on every build.

To build only the deployable site after the map artefacts exist, run `npm run site:build`; it regenerates the palette data, runs Nuxt generate, copies the root map data into `.output/public` and validates the result.

The build does not run the test suites. Run `npm test` for the Node suite and `npm run test:e2e:build` to build the site and run the Playwright smoke suite (`npm run test:e2e` reuses an existing build); see [4.screenshots.md](4.screenshots.md).
